# AQA README: учебный тестовый фреймворк для leap_year_py-vibe-code

## 1. Назначение

Проект содержит учебный набор автотестов для приложения проверки високосного года.

Цель - оформить минимальный тестовый фреймворк:

- тесты разделены по слоям;
- тестовые данные вынесены в параметризованные проверки;
- есть быстрый запуск без браузера;
- e2e-тесты вынесены отдельно;
- есть Gherkin-документация;
- есть Run Configurations для IntelliJ IDEA;
- зафиксирован известный пробел в требованиях через `xfail`.

Фреймворк построен на `pytest` как самом простом варианте для Python-проекта
(поддерживает параметризацию, fixtures, маркировку тестов, CLI-запуск и интеграцию с Playwright).

## 2. Что тестируется

Приложение состоит из нескольких пользовательских интерфейсов:

- `leap.py` - бизнес-логика и консольное меню;
- `app.py` - Flask web-интерфейс;
- `leap_gui.py` - Tkinter GUI;
- `templates/index.html` - HTML-шаблон Flask-приложения.

Основная логика находится в `leap.py`:

- `is_leap_year(year)` - определяет, високосный ли год;
- `explain_year(year)` - возвращает текстовое объяснение;
- `parse_positive_year(value)` - валидирует пользовательский ввод;
- `next_leap_years(start_year, count=5)` - ищет следующие високосные годы;
- CLI-функции меню - работают через `input()` и `print()`.

## 6. Pytest-настройки

Файл `pytest.ini`:

```ini
[pytest]
addopts = -m "not e2e"
testpaths = tests
python_files = test_*.py
python_functions = test_*
markers =
    e2e: browser end-to-end tests
```

Суть:

- обычный запуск `pytest` не запускает e2e;
- e2e запускаются отдельной командой
  (ускоряя повседневную проверку без нужды каждый раз стартовать браузер).

## 7. Уровни тестов

### 7.1. Unit-тесты бизнес-логики

Файлы:

```text
tests/test_leap_logic.py
tests/test_input_validation.py
tests/test_explain_year.py
tests/test_next_leap_years.py
```

Что проверяют:

- правило високосного года;
- делимость на `4`, `100`, `400`;
- обычные годы;
- граничные и исторически важные значения;
- валидный ввод;
- невалидный ввод;
- текстовые объяснения;
- поиск следующих високосных годов.

Именно этот слой увеличивает покрытие модульными автотестами:

- это самый быстрый и надежный слой;
- он проверяет чистые функции без UI;

Запуск:

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_leap_logic.py tests\test_input_validation.py tests\test_explain_year.py tests\test_next_leap_years.py
```

### 7.2. CLI-тесты

Файл:

```text
tests/test_cli.py
```

Что проверяет:

- запуск `leap.py` как консольной программы;
- выбор пунктов меню;
- проверку одного года;
- проверку нескольких годов;
- поиск следующих високосных годов;
- демонстрационный режим;
- выход из приложения;
- неизвестный пункт меню.

Суть:

- при проверке пользовательского сценария тесты проходят через `input()` и `print()`;
- благодаря этому они ближе к ручному тест-кейсу (но выполняются автоматически).

Запуск:

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_cli.py
```

### 7.3. Flask web-тесты

Файл:

```text
tests/test_web_flask.py
```

Что проверяет:

- открытие главной страницы;
- отправку формы через `POST`;
- режим проверки одного года;
- режим проверки нескольких годов;
- режим поиска следующих високосных годов;
- демонстрационный режим;
- ошибки валидации.

Суть:

- проверяется web-слой без запуска настоящего браузера;
- используется Flask `test_client`;
- тесты быстрее и стабильнее (чем browser e2e).

Запуск:

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_web_flask.py
```

### 7.4. Browser e2e-тесты

Файл:

```text
tests/test_web_e2e.py
```

Что проверяет:

- реальное открытие страницы в браузере Chromium;
- видимость формы;
- выбор режима в UI;
- ввод значения в поле;
- нажатие кнопки;
- отображение результата на странице.

Важно - почему e2e запускаются отдельно:

- они медленнее unit/Flask-тестов;
- требуют установленного Playwright-браузера;
- могут зависеть от локальной среды Windows;
- их не нужно прогонять при минорных изменениях.

Запуск:

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_web_e2e.py -m e2e --browser chromium -o addopts="" -s
```

Пояснение к параметрам:

- `tests\test_web_e2e.py` - запускаем только e2e-файл;
- `-m e2e` - выбираем тесты с маркером `e2e`;
- `--browser chromium` - явно указываем браузер;
- `-o addopts=""` - временно отключаем правило из `pytest.ini`, которое исключает e2e;
- `-s` - показываем вывод в консоли.

### 7.5. GUI Tkinter

Файл приложения:

```text
leap_gui.py
```

Важно: автотесты для GUI не добавлены осознанно.

Причина:

- `leap_gui.py` создает окно Tkinter сразу при импорте, что неудобно и нестабильно для unit-тестов;
- перед нормальным GUI-тестированием необходим рефакторинг кода
(вынести создание окна в функцию `main()` и отделить обработчики от инициализации UI).

Для ручного запуска GUI добавлена Run Configuration:

```text
Python: run leap_gui.py
```

## 8. Gherkin-документация

Файл:

```text
features/leap_year_cli.feature
```

Назначение:

- описать поведение CLI на языке, близком к ручным тест-кейсам;
- показать связь между требованиями, сценариями и автотестами;
- использовать Gherkin как документацию.

Важно:

- этот `.feature`-файл сейчас не является исполняемым автотестом;
- для выполнения Gherkin как тестов понадобились бы дополнительные инструменты (`pytest-bdd` или `behave`);
- в рамках текущего фреймворка он нужен как часть документации.

Что покрыто в Gherkin:

- проверка одного года;
- некорректный ввод;
- проверка нескольких годов;
- поиск следующих пяти високосных годов;
- демонстрационные проверки;
- выход из приложения;
- неизвестный пункт меню;
- известный пробел по значению `"20 24"`.

## 9. Run Configurations в IntelliJ IDEA

Проектные конфигурации сохранены в:

```text
.idea/runConfigurations/
```

Список конфигураций:

```text

pytest: CLI tests
pytest: Flask tests
pytest: e2e tests
```

Как пользоваться:

1. Открыть проект в IntelliJ IDEA.
2. Убедиться, что Project SDK указывает на `.\.venv\Scripts\python.exe`.
3. В верхнем правом выпадающем списке Run Configurations выбрать нужную конфигурацию.
4. Нажать зеленую кнопку запуска.

Если конфигурации не появились:

1. Выполнить `File -> Reload All from Disk`.
2. Если не помогло: `File -> Invalidate Caches... -> Invalidate and Restart`.

## 11. Известный падающий сценарий


```text
tests/test_input_validation.py
```

Он связан со значением:

```text
"20 24"
```

Текущее поведение приложения:

- `parse_positive_year("20 24")` удаляет пробел внутри строки;
- значение превращается в `"2024"`;
- приложение считает его валидным годом.

В демонстрационных целях зафиксировано отдельно, так как может являться спорным поведением
(ввод `"20 24"` может считаться как ошибкой, так и допустимой записью года);

Поэтому тест отмечен как `xfail`: он документирует спорный вопрос, но не ломает весь прогон.

## 13. Общее резюме

Готовым результатом считается состояние, при котором:

- зависимости для тестирования установлены в проектное виртуальное окружение `.venv`;
- Project SDK в IntelliJ IDEA указывает на интерпретатор из `.venv`;
- тестовый фреймворк запускается через `pytest`;
- бизнес-логика приложения покрыта отдельными unit-тестами;
- валидация пользовательского ввода проверяется отдельным набором тестов;
- текстовые объяснения результата проверяются отдельно;
- поиск следующих високосных годов покрыт отдельными тестами;
- CLI, Flask и e2e-проверки вынесены в отдельные тестовые слои и не смешаны с unit-тестами;
- в тестовый набор добавлены позитивные, негативные и граничные проверки;
- спорный случай `"20 24"` зафиксирован как известный пробел в требованиях через `xfail`;
- тот же пробел отражен в Gherkin-сценарии;
- быстрый запуск без e2e проходит командой `.\.venv\Scripts\python.exe -m pytest`;
- e2e-запуск проходит отдельной командой `.\.venv\Scripts\python.exe -m pytest tests\test_web_e2e.py -m e2e --browser chromium -o addopts="" -s`;
- в IntelliJ IDEA доступны Run Configurations для запуска всех основных тестовых слоев и приложений;
- итоговая документация по автотестам зафиксирована в `AQA_README.md`.


## 14. Точки роста

Дорожная карта дальнейшего развития:

- повысить воспроизводимость окружения: сохранить согласованное состояние окружения в `requirements-dev.txt` через `pip freeze` (что уменьшит риск того, что через несколько месяцев тот же проект соберется уже на других версиях `pytest`, `flask` или `pytest-playwright`);
- сделать запуск менее зависимым от одной OS, чтобы проект можно было воспроизвести не только в Windows-среде (рядом с PowerShell-командами добавить эквиваленты для macOS/Linux: `python3.11 -m venv .venv`, `source .venv/bin/activate`, `python -m pip install -r requirements-dev.txt`, `python -m pytest`);
- устранить риск расхождения между BDD-документацией и реальными тестами: либо подключить `pytest-bdd` и превратить `features/leap_year_cli.feature` в исполняемый сценарий (со step definitions), либо явно оставить Gherkin только как документацию и поддерживать его синхронно с обычными `pytest`-тестами;
- по мере роста набора тестов выделить общие фикстуры в `conftest.py` (если `client`, `live_server_url` или другие подготовительные объекты начнут использоваться в нескольких файлах, их лучше держать в одном месте, чтобы не копировать одинаковую настройку между слоями);
- добавить измеримую метрику покрытия: подключить `pytest-cov`, выполнять запуск вида `.\.venv\Scripts\python.exe -m pytest --cov=. --cov-report=term-missing` (и отслеживать не только количество пройденных тестов, но и то, какие строки кода все еще остаются без проверки);
- после появления большего числа тестовых слоев расширить систему маркеров: кроме `e2e`, добавить `unit`, `cli` и `flask`, отметить ими соответствующие тесты и зарегистрировать их в `pytest.ini` (тогда любой слой можно будет запускать короткими командами вроде `pytest -m unit` или `pytest -m cli`, без перечисления файлов вручную);
- точнее описать жизненный цикл e2e-проверок в документации: текущий `live_server_url` сам поднимает временный Flask-сервер через `werkzeug.make_server`, поэтому ручной запуск `app.py` перед e2e-тестами не нужен (это важно явно зафиксировать, чтобы следующий участник не тратил время на лишнюю подготовку);
- в случае приближения проекта к реальной командной разработке полезно автоматизировать контроль качества в CI: добавить workflow, который будет отдельно запускать быстрый набор тестов и e2e-проверки, чтобы воспроизводимость проверялась не только локально, но и на чистом окружении.
